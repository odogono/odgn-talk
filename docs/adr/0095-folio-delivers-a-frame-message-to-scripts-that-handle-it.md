# Folio delivers a frame message to Scripts that handle it

While a Play Session runs in Browse or Present, Folio sends `frame` once per displayed frame to every loaded Script that declares an `on frame` Handler. The Handler's one argument is the whole milliseconds since that Script's previous `frame`, 0 on its first. The message goes straight to the Script, never up the Message Path, so a Project Script's `frame` Handler does not catch frames meant for a game on one Page. When no loaded Script declares the Handler, Folio requests no frames at all. Leaving a Page stops its Page and Element Scripts' frames, as it cancels their waits, and the browser's `requestAnimationFrame` pauses them while the tab is hidden. Edit never runs frames.

A Script gets one `frame` at a time. If its previous `frame` Run is still running or waiting when the next display frame arrives, Folio skips that Script for the frame, and the next one it does get carries the time since the last it got, so no time is lost and the mailbox cannot fill. Each frame is a fresh Run, so a game loop never builds up one Run's fuel.

We chose this because games and animation need a steady tick, and the existing pattern, waiting and then sending yourself a message, puts timing bookkeeping in every Script and drifts with the Pump. Frames are what the browser already paces drawing by, and the opt-in by declaring a Handler means Projects without one cost nothing and authors have nothing to switch on or off.

We considered a `timer` Grant with start and stop Operations, which is more general but adds state a beginner must manage and still needs a cadence; a spec-level Host message every Host would implement, which commits the language to a display concept many Hosts lack; and delivering `frame` along the Message Path like `keyDown`, which would let one Handler catch every Page's frames. `frame` is a Folio Play message. A future Host that needs the same thing can adopt the same rules, and a spec-level message can follow if several do.
