# Operation Declarations may declare Argument Labels

An Operation Declaration may list `labels`, one word for each argument after the first, and then a call may write them between its arguments: `ask world to move "pass" to "red hangar"` calls `world`'s `move`, declared with `labels = ["to"]`, as `ask world to move "pass", "red hangar"` does. The labels are checked at load against the declaration, and they change nothing else: the Operation is still named `move`, and a labelled call is granted, charged, recorded and answered exactly as the positional call is, which stays valid. We chose this because Operation calls were the last calls written only with commas ([#1341](https://github.com/odogono/odgn-talk/issues/1341)). Mercenary's `move "pass", "red hangar"` doesn't say which place is which, and wrapping each Operation in a labelled Handler, or taking a map, is the noise [ADR 0055](0055-handlers-name-their-parameters-with-argument-labels-that-join-the-selector.md) removed for Handlers.

ADR 0055 made a Handler's labels part of its Selector, and rejected labels as sugar over a positional name, because a message can climb the Message Path to a Handler the loader can't see, and labels lost on the way would let `move knight from x` reach `on move piece to square` unchecked. An Operation call has no such path: the loader always sees the Operation Declaration in the Grant, and checks the call against it there. Keeping the name one word keeps everything a Host keys on the name unchanged, which are the grant, the cost, the `op` frame, the instruction and the Trace, and a Host that adds labels to an Operation breaks no Script, since the positional call still works.

The grammar needs no new decision. After a complete argument of `ask` or `tell`, a word in operator position was always a syntax error, and no operator reads `to`. `into` and `and` aren't labels, so a Result Target ([ADR 0112](0112-an-ask-may-name-a-result-target.md)) and `and wait` still end the arguments.

## Considered Options

- **Labels join the Operation's name as a Selector** (`move:to:`), as for Handlers. One meaning for Selector everywhere, and Host Commands would resolve by Selector unchanged, but the grant, the cost, the `op` frame and every Host's binding would key on `move:to:`, the positional call would name a different Operation, and adding labels would break every Script that calls it.
- **A labelled call required once an Operation declares labels.** Every call site would read the same way, but adding labels would be a breaking change for a Host.
- **A label on each argument Shape**, so some arguments could stay unlabelled. Heads and Command Calls label every argument after the first or none, and an Operation call should have the same shape.
- **Tooling-only labels**, like `description` and `examples` ([ADR 0076](0076-operation-declarations-carry-documentation-that-only-tooling-reads.md)), kept out of the Group Fingerprint. Labels decide whether a Script loads, so two Groups with different labels could load the same source differently.
- **A closed list of label words for Operations.** The Handler rule already decides labels on one token, and a second list would be one more thing for a Host to learn.

## Consequences

- **Declaring:** `labels` is optional, and when present has one entry per argument after the first, so its length is one less than `args`'. Each label follows [the Argument Label words](../../spec/02-grammar.md#argument-label-words): any Name, or `to`, but never `from`, `otherwise` or `with`. `DefineCapability` refuses any other label, and a list of the wrong length.
- **Calls:** an `ask`, a one-line `tell` and a `tell` block line take one argument, then `label argument` pairs, or a comma-separated list. A labelled call writes the declared labels in order, and may stop early where trailing Optional arguments are left off. A label that isn't the declared one at its position, or any label on an Operation that declares none, is the load error `wrong labels` at that label. The argument count is checked first, so a call with too many or too few arguments is still `wrong argument count`.
- **Host Commands:** an Operation marked `command` that declares labels has two spellings, its name (`move a, b`) and its Selector (`move a to b`, `move:to:`). Resolution, shadowing and clashes work on each Selector on its own, so a Handler `on move piece to square` shadows only the labelled spelling, and tooling Lints the shadowing as before. This narrows [ADR 0094](0094-host-commands-are-command-call-spellings-of-granted-operations.md), whose Host Commands never took labels.
- **Libraries:** a labelled call in a Library is checked against the Library's compilation declarations, and checked again against the importer's at its `use` line, as modes and argument counts are.
- **Hashing:** `labels` is part of the Operation Declaration, so it is in the Group Fingerprint, saves and restore's declaration matching, and changing an Operation's labels is a declaration mismatch.
- **The message layer:** `define-capability` and `compile-library` carry `labels`. A call's `op` frame, the `ask`, `tell` and `join-ask` instructions, the `call` record and pending calls don't change.
- **Tooling:** the Host Manifest carries `labels` in its Operation Declarations, so completion, hover, signature help and diagnostics read them with no Host-specific teaching. The formatter keeps whichever form a call is written in.
- **Narrows [ADR 0012](0012-capabilities-are-called-through-tell-and-ask.md):** arguments are still positional, but a call may name the positions with labels. **Narrows ADR 0055:** Capability Operations are no longer "not affected", and labels on an Operation are declaration metadata, not part of a name.
- **The language stays `1.0-rc.2`.** Every source that parsed before parses the same way.
