# A Fallback Handler receives the messages no clause matches

A Script may declare a Fallback Handler, `on any message m … end any message`. A message reaches it only when none of the Script's Handler Clauses for the message's Selector matches. That covers a Selector with no Handler, and one whose clauses all fail on arity, patterns or Guard. `m` is bound to the message as the map `{name, args}`. The Fallback gets this one chance before the message climbs the Message Path. A Fallback Run that ends without `pass` ends the message, and its result is the reply. `pass any message` climbs with the message unchanged. A `send … with` list may also spread a list into the arguments, `...e`, so a Fallback can forward a message whose argument count it doesn't know: `send (the name of m) with ...(the args of m) to other`. We chose both for two uses. A beginner's Script can answer "I don't know how to …" itself, instead of the message climbing silently to an `unhandled` that only the Host sees. And a Script can stand in front of another and forward what it doesn't handle itself, which ADR 0057's computed names made half possible. This is Smalltalk's `doesNotUnderstand:`, fitted to HyperTalk's Message Path. Settled in #333.

- **Only when nothing matched.** The Fallback runs after every Handler Clause for the Selector has failed, in the Script that received the message, and before the climb. An explicit `pass <name>` in a named clause means "not mine", so it climbs straight away and skips the Fallback.
- **Only ordinary messages.** A message sent to an object or to a Script, by a `send`, a Host Delivery or Request, or a climb, can reach a Fallback. These never do:
  - **Broadcasts.** A Script wants a Broadcast by Selector, as before. A Fallback would otherwise make every Script with one want every Broadcast, which breaks the rule that Scripts that don't want a Broadcast pay nothing.
  - **Decisions.** A clause without `, deciding` allows a Decision at dispatch (ADR 0031). A child's Fallback would then allow every Decision silently, before any parent could veto it.
  - **`error` messages.** One that no clause matches is still dropped.
  - **Local Command Calls.** These run in the caller's Run, and one with no matching clause still raises `no match`.
  - **Function Value calls,** which have no clauses.
- **An ordinary Handler otherwise.** A Fallback may have several clauses, tried in source order, each with a pattern on `m` and a Guard. If none matches, the message climbs. Each clause may have a Queueing Policy. `, deciding` and `, during` are load errors on a Fallback, and so is a Fallback in a Library, since imported Handlers are never entry points (ADR 0020). A Session Script may be extended with one.
- **The message map** is the one `wait for`'s `it` and `, during` already use: `name` is the Selector as text, and `args` is a list. So `send (the name of m) …` forwards to the same Selector.
- **Spread in `with`.** `...e` may stand for any number of the items in a receiver-last `send … with` list, anywhere and as often as in a list literal. A value that isn't a list raises `wrong kind`. Command Calls, function calls, `ask` and `tell` stay fixed-arity, since the loader checks their arity and whether they can suspend.
- **It doesn't reopen #177.** A Fallback sees only messages that have arrived, and never lists a Script's Handlers. A Script could already probe its own Handlers by sending to itself with `and wait` and catching `send failed`, reason `unhandled`. Nothing crosses the actor boundary (ADR 0004). The Session Host's `entry<n>` Handlers are named Handlers, so they're unaffected.

## Considered Options

- **A narrow whole-message resend, such as `send m to other`:** it would forward a message without a general spread. But it would be a second way to name a message in a `send`, and spread is useful on its own, for example in data-driven sends.
- **Spread as its own decision, blocking this one:** spread exists here to make forwarding possible, so they are recorded together.
- **Running the Fallback only for a Selector with no Handler:** a Handler whose clauses all fail would still climb unseen, which is the friendly failure this exists to give.
- **Letting `pass` fall into the Fallback:** `pass` is the Script's own decision that a message isn't its own. Catching it again in the same Script would make `pass` mean two things.
- **Letting Decisions or Broadcasts reach a Fallback:** see above. A deciding Fallback was also considered and rejected, because one Fallback would then hold every Decision on its path.
- **Reserving `any` as `all` is:** simpler grammar, but it would break any Script with a Handler named `any`. A two-token decision breaks nothing.
- **A new declaration word, such as `otherwise m`:** at the REPL, a statement that starts with a Name is a Command Call or an expression. A new declaration word would need a rule of its own there.
- **A single Fallback clause with no Queueing Policy:** simpler, but a Fallback couldn't route by name with Guards, the way every other Handler can.
- **A Lint for a Fallback that never passes:** a Fallback that answers every message is often exactly what was intended, for friendly failures. So the Lint looks for a likelier mistake instead.

## Consequences

- **Syntax:** `Handler` gains `'on' 'any' 'message' HandlerHead`, and `Pass` gains `'pass' 'any' 'message'`. `any` before `message` is a two-token decision, so `on any x` still names a Handler `any`. A Fallback's head is exactly one Destructuring pattern, then the usual Guard and suffixes. It ends with `end any message` or a bare `end`. `ExpressionList` in a receiver-last `send` takes `'...' Expression` items.
- **Glossary:** **Fallback Handler** joins CONTEXT.md, and **Message Path** says a Fallback gets one chance before the climb.
- **Load errors:** existing codes cover the new cases. A Fallback in a Library is `not in a library`, `, deciding` or `, during` on a Fallback is `bad suffixes`, and `pass any message` outside a Fallback, or `pass <name>` inside one, is `wrong message`. A head with other than one parameter, or with labels, is a syntax error, since the grammar gives a Fallback exactly one pattern.
- **Lowering:** a new body kind, `fallback`, named `any message`, with its clauses numbered from 1 and one parameter. Dispatch tries the Selector's clauses. If none matches and the message may reach a Fallback, it builds the message map without charge and tries the `fallback` clauses, each charged the `clause` rate as any clause is. `pass any message` lowers to `pass` with the operand `any message`. Spread lowers through the list-literal spread (`list 0`, `list-append`, `list-extend`). A static name is loaded as text, then one of three new instructions runs: `send-spread`, `send-spread-wait` or `join-send-spread`. Each pops the name, the argument list and the receiver, and checks the name as `send-named` does, against the list's length.
- **Trace and reports:** a Run started by a Fallback is an ordinary Run. Its `seg` or `preempt` start record and its `run` record carry `handler`, the message's Selector, and `fallback=yes`, and `clause` numbers the Fallback's clause. The `run end` report gains `fallback`. `unhandled` is reported only when the message reaches the end of its path.
- **Advanced Construct:** spread in `with` is tagged `advanced`, with listing the arguments in `with` as its Beginner Surface form. The Fallback Handler isn't tagged, because no Beginner Surface form does its job and friendly failures are a beginner's use (ADR 0027).
- **Tooling:** `unknown-message` still checks only Selectors, so it ignores a Fallback. `unreachable-clause` covers Fallback clauses. A new Lint, `fallback-routes-known` (hint in every profile), flags a Fallback clause that compares `the name of m` with a literal Selector the Script handles with named clauses. That clause runs only when those named clauses fail, which is rarely what was meant. The Host Manifest is unchanged: a Fallback doesn't widen the messages it declares.
- **Unchanged:** Broadcast "want", the Decision rules, `error` delivery, Save and Restore (a Fallback Run is saved as any Run is), and the Host boundary.
- **Delivery:** one change carries the spec, both Cores, the Lints and the corpus cases (ADR 0032).
- **The language stays `1.0-rc.2`,** as ADR 0055 recorded. Every source that parsed before parses the same way, and a message that reached `unhandled` before still does in a Script with no Fallback.
