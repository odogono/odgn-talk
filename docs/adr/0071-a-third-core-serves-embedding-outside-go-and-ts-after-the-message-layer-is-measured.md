# A third Core serves embedding outside Go and TS, after the Message Layer is measured

With both Cores passing the Conformance Corpus, the gate in ADR 0040 is met, and [#122](https://github.com/odogono/odgn-talk/issues/122) settles what a third Core would be for. A third Core exists only so that Hosts outside Go and TS can embed the language as they would Lua, through a C interface (`talk.h`) or a `wasm32-wasi` build. It never serves the browser, which keeps the TS Core, and it is never a reason to make either existing Core faster. It is not built until the Message Layer, the Go Core under `wasip1` behind a WASM runtime, has been built and measured for an Elixir Host and a minimal C Host on wasmtime, and has fallen short for one of them ([#532](https://github.com/odogono/odgn-talk/issues/532)). If it is built, it is written in Zig, or in Rust if Zig's pre-1.0 churn proves unworkable. Whether or not one is ever built, the Spec stays implementable without garbage collection. We chose this because every Core adds a third landing for each spec change and parity fix, for good, and the Message Layer reaches the same Hosts at no parity cost, so a third Core has to be earned by measurement. Memory safety comes before the widest reach, because the language exists to run hostile Scripts in a multi-tenant sandbox.

## Considered Options

- **A third Core as a faster or smaller browser runtime,** replacing the TS Core with Zig WASM: a WASM build of a Core this size would be about as small as the TS Core's bundle (163 KB brotli), and every event and Capability call would cross between JS and WASM, which is the single-core design ADR 0009 rejected.
- **A third Core for speed:** the 2026-10-08 benchmarks put both Cores at 110 to 1300 ns per Fuel unit, 30 to 70 times slower than gopher-lua and starlark-go, and the Go Core is already native code. The cost is in the per-step design that a third Core would share, so it is profiled in the existing Cores instead ([#533](https://github.com/odogono/odgn-talk/issues/533)).
- **C:** the widest reach, a stable toolchain and the Lua and SQLite way of shipping, but a C lexer, parser and interpreter fed hostile input is where exploitable bugs live. Undefined behaviour also threatens bit-for-bit parity across compilers. Faults would unwind through `longjmp` or hand-checked return codes.
- **Odin:** much like Zig for this job (explicit allocators, `u128`, C exports, WASM targets, no 1.0), but integer overflow wraps silently with no checked build, and it has fewer contributors still. Zig's `comptime` was no advantage over it, because every table is generated by `tools/` (ADR 0046).
- **Rust:** the strongest answer to hostile input, with checked reference counting, but a heavier toolchain. It stays as the fallback.
- **A translation of the Go or TS Core:** both lean on their garbage collectors, and a translation would carry one Core's accidents into another, making it the reference that ADR 0009 rules out.

## Consequences

- **Written from the Spec:** a third Core is written from the Spec and the corpus, and its tables are generated by emitters in `tools/` (ADR 0046). It is never called a port.
- **Targets:** native through `talk.h`, and `wasm32-wasi` for Hosts with a WASM runtime. The WASM build may later replace the Go `wasip1` build behind the Message Layer. It would likely be much smaller, an estimated 150 to 300 KB brotli against more than 1 MB, with no Go runtime inside the instance. Neither figure has been measured.
- **No garbage collection:** a Spec rule must be implementable without garbage collection, and without anything a language's runtime provides, such as exceptions, a scheduler or locale libraries. Value Semantics (ADR 0001) already keep Script values free of cycles, so reference counting with copy-on-write is complete. A future rule that lets Script values form a cycle breaks this constraint. This holds even if no third Core is ever built.
- **The measurement** records, for each Host: the payload, the cost per Pump and per Capability call, instantiation time and memory, and that a Script fault never traps the instance. Its thresholds are set in [#532](https://github.com/odogono/odgn-talk/issues/532) before measuring.
- **Unchanged:** ADR 0009's two Cores, the browser on the TS Core, and same-Core saves (ADR 0008).
- Narrows [ADR 0040](0040-a-third-native-core-is-deferred-until-both-cores-conform.md).
