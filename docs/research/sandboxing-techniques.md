# Sandboxing techniques for untrusted interpreted scripts

Research for [#6](https://github.com/odogono/odgn-talk/issues/6), part of the map [#1](https://github.com/odogono/odgn-talk/issues/1).
Vocabulary follows [`CONTEXT.md`](../../CONTEXT.md): Host, Script, Capability, Handler, Text Pattern.

**Question.** How do embeddable runtimes enforce deterministic CPU budgets, hard memory caps, recursion limits and capability-only I/O for untrusted Scripts that share one process? What can be achieved in Go and in JS/TS?

**Short answer.** Neither host platform can do it for us. Go has no per-goroutine memory limit, no way to kill a goroutine from outside, and a process-wide *soft* memory limit only. Bun ignores V8-style heap limits, browsers expose none, and SES (Hardened JS) explicitly says guest code may run forever and allocate without bound. Every runtime that meets our bar does it **inside the interpreter**. It counts steps in the dispatch loop, charges built-ins for the work they do, checks allocation sizes *before* allocating, caps frame depth itself, and injects every effect as a Capability object. So the deterministic budget has to be part of the language's semantics, specified the same way for the Go and TS implementations. It cannot be left to the Host.

Sources are cited inline. Code references point at the upstream default branch as read on 2026-09-27, unless a tag is given.

## 1. CPU: step counting, cost models and fuel

### What existing runtimes do

| Runtime | Mechanism | Deterministic? | Where the check happens | Blind spot |
|---|---|---|---|---|
| **starlark-go** (Go) | `Thread.SetMaxExecutionSteps(n)` plus `Thread.Cancel(reason)` | Yes (step count) | Every bytecode dispatch: `thread.Steps++; if thread.Steps >= thread.maxSteps {…}` and then a check of the atomic `cancelReason` ([interp.go](https://github.com/google/starlark-go/blob/master/starlark/interp.go)) | Built-ins: "There may be a delay before the interpreter observes the cancellation if the thread is currently in a call to a built-in function" ([eval.go](https://github.com/google/starlark-go/blob/master/starlark/eval.go)) |
| **canonical/starlark** (Go fork) | Same, plus `thread.AddSteps` / `CheckSteps`, which built-ins call in proportion to the work they do | Yes | Interpreter loop plus every "CPUSafe" built-in ([safety.md](https://github.com/canonical/starlark/blob/master/doc/safety.md)) | Only as good as each built-in's declared cost. Enforced "through testing", not by construction |
| **CEL / cel-go** (Go) | Static `Env.EstimateCost` gives a `{Min, Max}` range before running. `CostLimit(n)` aborts at runtime with "runtime cost limit exceeded" | Yes | Per operation and per function call ([options.go v0.23.0](https://github.com/google/cel-go/blob/v0.23.0/cel/options.go), [env.go](https://github.com/google/cel-go/blob/v0.23.0/cel/env.go), [checker/cost.go](https://github.com/google/cel-go/blob/v0.23.0/checker/cost.go)) | Only works because CEL is non-Turing-complete. "CEL programs cannot loop forever" ([langdef](https://github.com/google/cel-spec/blob/master/doc/langdef.md)) |
| **goja** (Go, JS engine) | `Runtime.Interrupt(v)` sets an atomic flag. The VM checks it in its run loop | No (wall-clock, driven by the Host) | VM run loop (`atomic.LoadUint32(&vm.interrupted)` in [vm.go](https://github.com/dop251/goja/blob/master/vm.go)) | "It only works while in JavaScript code, it does not interrupt native Go functions (which includes all built-ins)" ([runtime.go](https://github.com/dop251/goja/blob/master/runtime.go)) |
| **QuickJS** (C, used from JS through WASM) | `JS_SetInterruptHandler(rt, cb, opaque)`. The callback runs every 10,000 poll points (`JS_INTERRUPT_COUNTER_INIT 10000`) | Only if the callback counts calls instead of reading a clock | `OP_goto*` back-edges, calls, the `instanceof` prototype walk ([quickjs.c](https://github.com/bellard/quickjs/blob/master/quickjs.c)), **and inside the regex engine** (`lre_poll_timeout` in [libregexp.c](https://github.com/bellard/quickjs/blob/master/libregexp.c)) | Native built-ins that do not poll |
| **Luau** (C++) | Global `interrupt` callback "gets called at safepoints (loop back edges, call/ret, gc)" ([lua.h](https://github.com/luau-lang/luau/blob/master/VM/include/lua.h)) | Host's choice | Safepoints | "…if the script manages to find a way to call a single C function that takes a lot of time" ([luau.org/sandbox](https://luau.org/sandbox)) |
| **wasmtime** (Rust, for comparison) | `Config::consume_fuel`: "deterministically prevent infinitely-executing WebAssembly code by instrumenting generated code". Also `epoch_interruption`, which is cheaper and "not deterministic" | Fuel yes, epochs no | Per operator, with per-byte/per-element variable costs for bulk operators ([config.rs](https://github.com/bytecodealliance/wasmtime/blob/main/crates/wasmtime/src/config.rs)) | none of note |
| **wazero** (Go WASM runtime) | **No fuel API** (no "fuel" in `config.go`). Only `WithCloseOnContextDone`, which inserts "periodical checks" for context cancellation or timeout ([config.go](https://github.com/wazero/wazero/blob/main/config.go)) | No (wall-clock) | Periodic checks in compiled code | Not deterministic |
| **Neil Fraser's JS-Interpreter** (pure JS) | The Host calls `step()` repeatedly. "Infinite loops are handled by calling the `step` function a maximum number of times" ([docs](https://neil.fraser.name/software/JS-Interpreter/docs.html)) | Yes | Every AST step | "about 200 times slower than native JavaScript" |

### Deterministic vs wall-clock

- A **step or fuel** budget is a property of the Script and its inputs, independent of load and hardware. Kubernetes says of CEL: "Cost units are independent of system load and hardware. Cost units are also deterministic; for any given CEL expression and input data, evaluation … will always result in the same cost" ([k8s CEL docs](https://kubernetes.io/docs/reference/using-api/cel/#resource-constraints)). This is what makes budgets reproducible, testable in a conformance corpus, and fair between tenants.
- A **wall-clock** limit (goja `Interrupt`, wazero context, QuickJS deadline handlers, isolated-vm `timeout`) is still useful as a backstop. It is not deterministic, and on its own it cannot give "same result on every Host".
- Counting granularity is a trade-off. Starlark checks every instruction. QuickJS amortises with a countdown of 10,000. wasmtime's docs note that precise fuel "is somewhat expensive" compared with epochs ([config.rs](https://github.com/bytecodealliance/wasmtime/blob/main/crates/wasmtime/src/config.rs)). A decrement-and-branch per dispatch is cheap compared with the dispatch itself in a Go or TS interpreter.

### Built-ins must be charged for their work

A step counter in the dispatch loop only meters *interpreted* code. Every runtime above lists the same hole: one native call that does a lot of work. There are two fixes:

1. **Charge in proportion to input size, before doing the work.** canonical/starlark: "declare a number of steps proportional to the amount of work to be done just before doing it … the number of steps is proportional to the work done and not the actual CPU usage" ([safety.md](https://github.com/canonical/starlark/blob/master/doc/safety.md)). CEL gives each function an estimated cost. For regex, Kubernetes charges `length(regexString)*length(inputString)`, which "reflects the worst case time complexity of Go's RE2 implementation" ([k8s CEL docs](https://kubernetes.io/docs/reference/using-api/cel/#resource-constraints)). wasmtime gives bulk operators "per-byte, per-element, and per-page costs" ([config.rs](https://github.com/bytecodealliance/wasmtime/blob/main/crates/wasmtime/src/config.rs)).
2. **Make long built-ins poll.** QuickJS's regex matcher polls the interrupt handler every 10,000 steps ([libregexp.c](https://github.com/bellard/quickjs/blob/master/libregexp.c)). canonical/starlark's `SafeIterate` and `SafeStringBuilder` count steps as they go ([safety.md](https://github.com/canonical/starlark/blob/master/doc/safety.md)).

**Static cost estimation** (CEL) works only for a terminating, loop-free language. We have loops, Handlers and recursion, so a static bound is at best a lint or tooling feature. Starlark gets bounded execution another way. It bans recursion unless a flag is set and allows only `for` over finite sequences, so programs "can not be Turing complete unless the `-recursion` flag is specified" ([spec.md](https://github.com/google/starlark-go/blob/master/doc/spec.md)). Both routes cost expressiveness that a general HyperTalk-style language probably needs. A runtime fuel meter is required either way.

### Go vs JS/TS

- **Go:** step counting in the interpreter loop is idiomatic and proven (starlark-go, cel-go). Goroutines are preemptible ("Goroutines are now asynchronously preemptible … loops without function calls no longer potentially deadlock the scheduler", [Go 1.14 notes](https://go.dev/doc/go1.14)). One tenant per goroutine therefore gets fair CPU sharing from the Go scheduler, and the fuel meter decides *when to stop*.
- **JS/TS:** an interpreter written in TS runs on the Host's single event-loop thread. A long synchronous run blocks every tenant *and* the Host. So the fuel meter must also **time-slice**: run up to K steps, then yield to the event loop and resume. This is the pattern JS-Interpreter recommends ("calling `step` indefinitely many times but using a setTimeout between each call", [docs](https://neil.fraser.name/software/JS-Interpreter/docs.html)). To slice like this, the interpreter needs resumable state (explicit frames) instead of deep native recursion. The same machinery serves suspension mid-Handler.

## 2. Memory: per-Script accounting and caps

### What the host platforms give you

- **Go:** `debug.SetMemoryLimit` is a *soft*, **process-wide** limit covering "all memory mapped, managed, and not released by the Go runtime" ([runtime/debug](https://github.com/golang/go/blob/master/src/runtime/debug/garbage.go)). The GC guide explains why it is soft: "an indefinite stall is worse than an out-of-memory condition … For this reason, the memory limit is defined to be soft" ([gc-guide](https://go.dev/doc/gc-guide)). Go has no per-goroutine heap and no way to attribute heap objects to a goroutine. `debug.SetMaxStack` is per goroutine, but going over it crashes: "If any goroutine exceeds this limit while growing its stack, the program crashes" ([runtime/debug](https://github.com/golang/go/blob/master/src/runtime/debug/garbage.go)). That is the opposite of isolation.
- **V8 (Node):** a separate isolate per Worker, with `resourceLimits` (`maxOldGenerationSizeMb`, `stackSizeMb`, …). Hitting a limit terminates the Worker. The limits exclude `ArrayBuffer`s, and "the process may still abort if it encounters a global out-of-memory situation" ([Node worker_threads](https://github.com/nodejs/node/blob/main/doc/api/worker_threads.md)). isolated-vm offers an in-process isolate `memoryLimit`, but warns: "more of a guideline instead of a strict limit. A determined attacker could use 2-3 times this limit". It is also a Node native addon in "maintenance mode" ([isolated-vm README](https://github.com/laverdet/isolated-vm)).
- **Bun (JSC):** "`Worker` ignores the `resourceLimits` … options" ([Bun Node compat](https://github.com/oven-sh/bun/blob/main/docs/runtime/nodejs-compat.mdx)). The only knob is `smol: true`, which "sets `JSC::HeapSize` to be `Small`". That tunes the heap. It is not a cap ([Bun Workers](https://github.com/oven-sh/bun/blob/main/docs/runtime/workers.mdx)).
- **Browser:** no API caps a realm's or Worker's heap. `performance.measureUserAgentSpecificMemory()` is asynchronous, measures at agent-cluster level, requires cross-origin isolation, is Chromium-only, and is meant for aggregate telemetry, not enforcement ([WICG spec](https://wicg.github.io/performance-measure-memory/)).
- **SES / Hardened JS:** a Compartment guest "can … allocate arbitrary amounts of memory" and "execute for an indefinite amount of time" ([SES README, Security claims and caveats](https://github.com/endojs/endo/blob/master/packages/ses/README.md)).
- **WASM linear memory** gives a real hard cap per *module instance*. See wazero `WithMemoryLimitPages` ([config.go](https://github.com/wazero/wazero/blob/main/config.go)) and the wasmtime `ResourceLimiter::memory_growing` hook ([limits.rs](https://github.com/bytecodealliance/wasmtime/blob/main/crates/wasmtime/src/runtime/limits.rs)). QuickJS-in-WASM uses this: `JS_SetMemoryLimit` makes `js_def_malloc` return `NULL` once `malloc_size + size > malloc_limit` ([quickjs.c](https://github.com/bellard/quickjs/blob/master/quickjs.c)), exposed in JS as `runtime.setMemoryLimit` ([quickjs-emscripten](https://github.com/justjake/quickjs-emscripten)). The limit is per `JSRuntime` (one heap), not per context. It also requires C, which our Go/TS-only constraint excludes for the interpreter itself.

**Conclusion: in both Go and JS/TS, a hard per-Script memory cap is only achievable through interpreter-level accounting.** The engines that have real caps (QuickJS, Luau, WASM) own their allocator. Luau: "By default, no memory limits are imposed … this is easy to configure from the host for Luau allocations" through the `lua_Alloc` allocator passed to `lua_newstate` ([luau.org/sandbox](https://luau.org/sandbox), [lua.h](https://github.com/luau-lang/luau/blob/master/VM/include/lua.h)). A Go or TS interpreter does not own the allocator, so it must count.

### How interpreter-level accounting is done in practice (Go)

canonical/starlark is the most direct precedent. It is a Go interpreter with a per-thread memory budget (`SetMaxAllocs`, `AddAllocs`, `CheckAllocs`) ([README](https://github.com/canonical/starlark), [safety.md](https://github.com/canonical/starlark/blob/master/doc/safety.md)). Its lessons:

- It is "a best effort system via a contract … The contract is upheld through testing", because "the Go interpreter doesn't offer a good basis for such hard enforcement".
- **Check before allocating.** A size template lets "the allocation check … be moved *before* the allocation happens".
- **Persistent allocations are always counted. Transient ones only when large.** Transient spikes are bounded with `CheckAllocs` or paired `AddAllocs(+n)` / `AddAllocs(-n)`.
- **Frees are ignored.** "Given the expected infrequency of garbage collection cycles and the short-lived nature of safe Starlark execution, the freeing of persistent values can be ignored." The budget is really a *monotonic allocation budget* per execution.
- **Overflow-safe size arithmetic** (`SafeInt`, `SafeMul`). Without it, `list * n` can overflow and make `make` allocate the wrong size or panic.
- Hidden Go allocations (interface boxing, map growth) make exact counting "prohibitively complex". Estimates such as `EstimateSize` are used and checked by a test harness (`startest`).

In JS/TS the situation is the same or worse. No allocator hook exists, and object sizes are engine-specific and hidden. An interpreter can only charge a *model* size per value (for example, bytes per string code unit plus fixed overhead per list or map entry). The model only needs to be deterministic and conservative. It does not need to match the engine's actual heap use.

### Live vs allocated memory

Knowing when a value is freed needs host GC signals (`FinalizationRegistry`, `runtime.AddCleanup`). Those are asynchronous and not deterministic, so a *live-heap* cap can't be deterministic on a GC'd host. The deterministic options are:

1. A **per-activation allocation budget** (canonical/starlark model). Every byte allocated during one Handler run counts, and frees are ignored.
2. A **persistent-state size cap**, measured by walking the Script's reachable persistent state (globals, stored continuations) at deterministic points such as the end of a Handler or a suspension point.

## 3. Recursion, stack depth, output size and allocation rate

- **Explicit depth counters are the norm.** goja: `SetMaxCallStackSize` throws a catchable `*StackOverflowError`. Its default is `math.MaxInt32`, which is effectively unlimited, so the Host must set it ([runtime.go](https://github.com/dop251/goja/blob/master/runtime.go)). QuickJS: `JS_SetMaxStackSize` ([quickjs.h](https://github.com/bellard/quickjs/blob/master/quickjs.h)). canonical/starlark: "Starlark recursion now has a hard limit" ([README](https://github.com/canonical/starlark)). Upstream Starlark bans recursion outright unless a flag allows it ([spec.md](https://github.com/google/starlark-go/blob/master/doc/spec.md)).
- **Do not rely on the host's native stack.** In Go, a tree-walking interpreter that recurses on the goroutine stack grows it up to `SetMaxStack` (1 GB on 64-bit by default), then *crashes the whole process* ([runtime/debug](https://github.com/golang/go/blob/master/src/runtime/debug/garbage.go)). In JS the native limit is engine- and thread-specific (Node's Worker `stackSizeMb` defaults to 4, [worker_threads](https://github.com/nodejs/node/blob/main/doc/api/worker_threads.md)), so the depth at which `RangeError` fires would differ between Hosts. That breaks determinism. The fix is a language-level frame limit, preferably with frames on the heap, which suspension needs anyway.
- **Charge frame memory too.** Each frame should count against the memory budget, so deep but legal recursion cannot get around the cap.
- **Output and value size.** canonical/starlark routes string building through `SafeStringBuilder`, which "will both count the allocations for the string it constructed and the steps required to do so" ([safety.md](https://github.com/canonical/starlark/blob/master/doc/safety.md)). CEL's spec notes that concatenation "dramatically increases space complexity" and that nested macros are the "primary source of exponential behavior" ([langdef](https://github.com/google/cel-spec/blob/master/doc/langdef.md)). Chunk Expressions such as `put x after line 3 of y`, string repetition and list growth all need pre-checked size costs.
- **Allocation rate.** No surveyed runtime has a separate rate limit. Charging steps per byte allocated has the same effect in deterministic units: allocation-heavy code uses up its fuel faster. Output that goes through a Capability (logging, sending messages) is a Host concern and should be limited at the Capability (quota per call or per activation).

## 4. Capability-only I/O

- **Start from nothing, then add.** Starlark: programs "have no external side effects", and core execution is deterministic with "no sources of random numbers, clocks, or unspecified iterators" ([spec.md](https://github.com/google/starlark-go/blob/master/doc/spec.md)). Every effect is a Host-provided built-in in the predeclared environment. JS-Interpreter is "secure by default … no external APIs except as provided by the developer", added through `initFunc` / `createNativeFunction` / `createAsyncFunction` ([docs](https://neil.fraser.name/software/JS-Interpreter/docs.html)).
- **Subtract from an existing stdlib (Luau).** `io.` and `package.` are removed, `os.` is cut down to clock and date functions, and `load`, `dofile`, `loadfile` and `string.dump` are removed. Bytecode loading is refused because "the VM assumes that the bytecode was generated by the Luau compiler". Built-in libraries are marked read-only, and each Script gets its own global table that falls back to the built-ins through `__index` ([luau.org/sandbox](https://luau.org/sandbox)). Subtraction is riskier than starting empty: anything forgotten becomes ambient authority.
- **Object capabilities (SES / Hardened JS).** Compartments "receive no ambient authority … can be selectively endowed with powerful arguments, globals, or modules". Shared intrinsics are frozen so tenants cannot change what they share. A single guest "cannot initially perform any I/O … and specifically cannot measure the passage of time at any resolution". Two guests in a frozen compartment cannot "communicate, as they would if they had shared access to mutable state like … `Math.random()`" ([SES README](https://github.com/endojs/endo/blob/master/packages/ses/README.md)). Ideas to take: frozen shared stdlib, no clock or randomness unless granted, and authority passed only as object references.
- **How Hosts inject Capabilities.** Every system above does the same thing. The Host builds a per-Script environment (Starlark predeclared `StringDict`, Luau per-script globals, SES `Compartment` endowments, JS-Interpreter `initFunc`) and puts capability objects in it. A capability can be attenuated before it is granted (for example, an HTTP client limited to one origin). The Script can only use what it can name.
- **JS/TS note:** SES is a way to run *JavaScript* safely, and it does nothing for CPU or memory ([SES caveats](https://github.com/endojs/endo/blob/master/packages/ses/README.md)). An interpreter for our own language does not need SES to isolate Scripts from each other, because Scripts never touch host JS objects directly. The object-capability discipline has to be built into the interpreter's value model instead.

**Go vs JS/TS:** there is no platform difference. Capability-only I/O is purely a design property of the interpreter and its host-binding API, and it is equally achievable in both.

## 5. Text Patterns and ReDoS

- **RE2 semantics guarantee linear time.** Go's `regexp`: "guaranteed to run in time linear in the size of the input. (This is a property not guaranteed by most open source implementations …)" ([regexp.go](https://github.com/golang/go/blob/master/src/regexp/regexp.go)). The cost is features: "backreferences and generalized assertions are not available" ([re2.h](https://github.com/google/re2/blob/main/re2/re2.h), [RE2 syntax](https://github.com/google/re2/wiki/Syntax)). The bound is O(pattern × input). Kubernetes costs CEL `matches` as `length(regex)*length(input)`, and the CEL spec says "Time complexity is proportional to the product of the sizes of the arguments as guaranteed by the RE2 design" ([k8s CEL](https://kubernetes.io/docs/reference/using-api/cel/#resource-constraints), [langdef](https://github.com/google/cel-spec/blob/master/doc/langdef.md)).
- **Compile-size limits matter too.** Go's `regexp/syntax` rejects patterns whose tree nests deeper than `maxHeight = 1000` (`ErrNestingDepth`) or whose compiled program is too large (`ErrLarge`, about 128 MB of instructions) ([parse.go](https://github.com/golang/go/blob/master/src/regexp/syntax/parse.go)). RE2 has a `max_mem` budget for the program and its DFA cache ([re2.h](https://github.com/google/re2/blob/main/re2/re2.h)). Counted repetition such as `4 digits` or `{200,500}` expands the program, so it needs a limit.
- **Go's `regexp` cannot be metered or cancelled mid-match.** It is linear, but its API takes no context or step budget. A Host can only pre-charge cost (the Kubernetes approach) and cap input size.
- **JS options:**
  - Native `RegExp` (V8 Irregexp, JSC YARR) backtracks, so ReDoS is possible. V8's linear engine exists behind flags (`--enable-experimental-regexp-engine` with the `/l` flag, or a fallback after `--regexp-backtracks-before-fallback`, default 50,000). It is "not enabled by default" and does not support backreferences, lookaround, large counted repetition, or the `u` and `i` flags ([v8.dev blog](https://v8.dev/blog/non-backtracking-regexp)). It isn't available in Bun or in browsers we don't control.
  - **re2-wasm**: RE2 compiled to WASM. It "lacks two features: backreferences and lookahead assertions", works only in Unicode mode, is "not an officially supported Google product", and was last pushed in 2023 ([re2-wasm](https://github.com/google/re2-wasm)).
  - **RE2JS**: a pure-JS port that "achieves full architectural parity with the Go regexp implementation" and guarantees linear time "for both Node.js and browser applications" ([re2js](https://github.com/le0pard/re2js)).
  - goja (Go-hosted JS) falls back to `dlclark/regexp2`, a backtracking engine, for features Go's `regexp` lacks ([regexp.go](https://github.com/dop251/goja/blob/master/regexp.go)). That brings ReDoS back into a Go Host, and since `Interrupt` does not reach built-ins, such a match cannot be interrupted.
  - QuickJS shows the other design: a backtracking engine that **polls the interrupt budget** ([libregexp.c](https://github.com/bellard/quickjs/blob/master/libregexp.c)). Pathological patterns stay possible, but they burn the tenant's budget instead of hanging the Host.
- **What linear time costs:** no backreferences, no general lookaround, and bounded counted repetition. There is one exception: captureless lookbehinds *can* be matched in linear time. RE2JS offers this behind an opt-in `LOOKBEHINDS` flag, based on EPFL research ([re2js README](https://github.com/le0pard/re2js), [arXiv 2311.17620](https://arxiv.org/pdf/2311.17620)). Captures and alternation are fine in a Pike VM. For readable Text Patterns such as `<"ID-", num: 4 digits, " ", name: word>`, the missing features are rarely needed. Named captures, character classes, repetition and alternation all fit within RE2 semantics.

**Go vs JS/TS:** the host regex engines differ (Go is linear, JS backtracks) and have slightly different syntax and Unicode semantics. Using either one for Text Patterns would give different results and different cost behaviour on each Host.

## 6. Stopping a runaway Script cleanly

- **Cooperative cancellation is the only in-process option.** Starlark's `Cancel` is "safe to call … from any goroutine" and is seen at the next instruction ([eval.go](https://github.com/google/starlark-go/blob/master/starlark/eval.go)). goja's `Interrupt` does the same through an atomic flag. Luau's interrupt "is safe to set from an arbitrary thread" ([lua.h](https://github.com/luau-lang/luau/blob/master/VM/include/lua.h)). All of them only stop *interpreted* code. A built-in that does not poll delays the stop (goja, Luau, Starlark caveats above). canonical/starlark states this as a contract: "`TimeSafe`: when the executing thread is cancelled, such a function will stop within a reasonable amount of time" ([safety.md](https://github.com/canonical/starlark/blob/master/doc/safety.md)). It also removes `Uncancel`: "Threads cannot be uncancelled" ([README](https://github.com/canonical/starlark)).
- **Go gives no hard kill.** Go cancellation is cooperative through `context.Context` ("A Context may be canceled to indicate that work done on its behalf should stop", [context.go](https://github.com/golang/go/blob/master/src/context/context.go)). A goroutine stuck in a non-polling built-in can't be stopped. Some failures escape `recover` and take down *every* tenant: goroutine stack overflow ([SetMaxStack](https://github.com/golang/go/blob/master/src/runtime/debug/garbage.go)) and real OOM. So the interpreter's own depth and memory checks must stop a Script well before the runtime has to.
- **JS gives a hard kill, but only at Worker granularity.** HTML's "terminate a worker" discards queued tasks and aborts "the script currently running in the worker" ([HTML spec](https://html.spec.whatwg.org/multipage/workers.html)). Bun's `worker.terminate()` "makes the worker exit as soon as possible" ([Bun Workers](https://github.com/oven-sh/bun/blob/main/docs/runtime/workers.mdx)), and Node's is similar ([worker_threads](https://github.com/nodejs/node/blob/main/doc/api/worker_threads.md)). A Worker per tenant costs a thread and a heap each. The realistic use is a pool of Workers, each running many tenants' interpreters, terminated only as a last resort. Terminating one kills all its co-tenants.
- **In-flight suspended Handlers.** Once a Script is suspended waiting on a Capability, its continuation is just data held by the Host. Stopping it cleanly means:
  1. mark the Script cancelled, so it is never resumed;
  2. cancel outstanding Capability operations through a cancellation token supplied with each call (Go `context.Context`, JS `AbortSignal`);
  3. drop results that arrive for a cancelled Script, with no callback into interpreter state;
  4. release its continuation and its charged memory.

  wazero's `WithCloseOnContextDone` is a similar shape: when execution is cancelled, "`api.Module` is closed" ([config.go](https://github.com/wazero/wazero/blob/main/config.go)). The instance is torn down as a unit.
- **Neighbour safety.** Tenants must share no mutable state (per-Script globals, frozen stdlib, as in Luau and SES above). Then stopping one Script cannot leave another holding half-updated shared data. Budgets should be per Script, or per activation, never global.

## What is achievable, Go vs JS/TS

| Requirement | Go | JS/TS (Bun, browser) |
|---|---|---|
| Deterministic CPU budget | Yes, through interpreter step counting plus charged built-ins (starlark-go, cel-go precedent) | Yes, through the same method. It also needs time-slicing, because interpreter code shares the event loop |
| Wall-clock backstop | `context` deadline plus `Cancel` from a watchdog goroutine | Deadline check inside the step loop. `Worker.terminate()` as a coarse last resort |
| Hard per-Script memory cap | **Only** interpreter accounting (canonical/starlark). The runtime limit is soft and process-wide | **Only** interpreter accounting. Bun ignores `resourceLimits`, browsers have no cap, SES does not help |
| Recursion limit | Interpreter frame counter. Native stack overflow crashes the process | Interpreter frame counter. Native `RangeError` depth varies by engine |
| Capability-only I/O | Yes (interpreter design) | Yes (interpreter design) |
| Linear-time Text Patterns | Go `regexp` is linear but cannot be metered. A custom engine is better | Native `RegExp` is unsafe. RE2JS or re2-wasm work. A custom engine is better |
| Clean stop | Cooperative only. No goroutine kill | Cooperative in-process, plus Worker termination as a coarse hard kill |

## Implications for our language

These requirements fall on the **interpreter and the spec**. The Host platforms cannot supply them.

1. **Fuel is part of the language semantics.** Define an abstract step cost per operation in the spec, as CEL's cost units do, so that the Go and TS interpreters charge *identical* fuel for identical Scripts and inputs. Put budget-exhaustion points in the conformance corpus (Script, input, budget, expected outcome). The exact step unit can stay unspecified ("may change", as Starlark says). Cross-host parity cannot: whatever we choose must be the same on all Hosts.
2. **The fuel check lives in the dispatch loop and in every built-in.** Each stdlib function, Chunk Expression, Unit conversion and Text Pattern match charges fuel in proportion to input size, *before* the work where possible, and polls during long loops. Host-provided Capabilities must be able to charge fuel too. The host API should give them a budget handle, like canonical/starlark's `AddSteps` / `AddAllocs`.
3. **Memory is modelled, not measured.** Specify a deterministic model size per value kind and charge it at construction, checked before allocating. Use overflow-safe size arithmetic. Recommended shape: a **per-activation allocation budget** (monotonic, frees ignored) plus a **persistent-state cap** checked at deterministic points (end of Handler, suspension). Do not try to track live-heap size on a GC'd host. Per-value maxima (maximum string length, maximum list length) are a cheap first line of defence.
4. **Heap-allocated frames with a language-level depth limit.** Do not recurse on the Go or JS native stack for Script calls. That gives deterministic depth errors on every Host, lets the TS implementation time-slice, and supports suspension mid-Handler. It points toward a bytecode or CPS-style VM with an explicit stack, which is an input to the runtime-architecture and execution-model tickets.
5. **Text Patterns get their own engine, written twice.** Compile Text Patterns to a Thompson NFA / Pike VM (RE2 semantics) implemented the same way in Go and TS. The engine charges fuel per NFA step and has compile-time limits on nesting depth, counted repetition and program size, as Go's `maxHeight` and RE2's `max_mem` do. That gives linear time, the same results on every Host, and metering. Host `regexp`/`RegExp` cannot provide the last two. The cost is no backreferences and no lookaround. If they are ever wanted, they could be an explicit advanced-layer feature on a fuel-metered backtracker (the QuickJS model), where a bad pattern burns the tenant's budget instead of hanging the Host.
6. **No ambient authority, including time and randomness.** The core language has no clock, randomness, I/O or environment access. The Host grants each one as a Capability object in a per-Script environment. The shared stdlib is immutable. Tenants share no mutable values. Capabilities can be attenuated before granting. This keeps core execution deterministic (as Starlark does) and removes timing side channels between tenants (as SES does).
7. **Cancellation is sticky and flows through suspension.** A cancelled Script cannot be un-cancelled. Every async Capability call receives a cancellation token (context / AbortSignal). Suspended continuations are dropped on cancel, and late results are discarded. The Host API needs a "stop Script" operation that works whether the Script is running, queued or suspended.
8. **The trusted base is the built-ins.** Each precedent's sandbox is only as good as its native functions (goja, Luau and Starlark all say so). We should adopt canonical/starlark's approach: each built-in declares which safety properties it meets (CPU, memory, time, I/O), the Host can refuse built-ins that don't meet what it requires, and a test harness checks that declared costs scale with input.
9. **Keep a wall-clock watchdog as a backstop.** It is not the budget, but it catches bugs in the cost model. In Go it is a watchdog calling `Cancel`. In TS it is a deadline check in the slice loop, with Worker termination as a last resort for Hosts that run tenants in Worker pools.
