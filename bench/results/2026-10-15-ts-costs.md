# TS Cost Model specialization (#942)

Baseline: `f51ad856e37d802b8865bb2870c3adebc293e7d1`. The after variant is this change on that base. Only `impl/ts/src/costs.ts` is substituted in the before bundle; all other current sources, workloads, limits and settings are identical. The after bundle includes the generated charge and leaf-size evaluators. This isolates accounting from the other TS performance scopes. No Spec, corpus expectation, Value representation or save-format change is included.

Bun 1.4.3, macOS arm64, Apple M5, 10 cores, 24 GiB; default JIT and GC settings. Paired timings exclude Load and profiling. Both self-contained bundles run in one process with separate loaded Groups. Each workload gets 20 warm-up Runs per variant, followed by three rounds of seven paired batches of 20 full-size Runs, alternating AB/BA. Each table range covers all 21 batch means, not individual Run latency. Each measured batch checks its final output, exact Fuel and logical allocation; all matched. The raw JSON records N, Fuel Slice and expected result/accounting for every workload.

The workstation was shared with other work. Starting/ending load averages were [8.96142578125, 11.4453125, 7.806640625] / [6.11865234375, 9.46728515625, 7.5634765625]. These are advisory observations, with no confidence intervals. A first pass using whole before/after processes suffered large temporal drift and was not used for the conclusions below; its [raw timings](2026-10-15-ts-costs/initial-process-timings.json) are retained.

Addition fell from 3.968 to 3.546 ms (10.6%); calls fell from 3.513 to 3.266 ms (7.0%); List construction fell from 2.449 to 2.254 ms (8.0%). List append was effectively flat, and the 10-Fuel Slice case showed no clear improvement. Map updates, text building and immediate Host calls show substantial variability. The Host-call pooled slowdown did not reproduce in a separate identical targeted comparison: 1.900 → 1.631 ms, with round ratios 1.09×, 1.30× and 1.05×. Both observations are retained; this does not establish a universal Host-call improvement.

## Separate heap and GC observations

Each variant runs in a separate process. After warm-up and a forced full GC, the probe records JSC/process memory, executes 100 validated Runs, records memory again, then forces another full GC and records its duration and retained memory. Snapshots and earlier workload observations themselves retain bookkeeping memory. These figures describe observed heap occupancy, not total bytes allocated; there is one final GC observation per workload and variant. Generated functions add some retained startup state. There is no claim of a uniform retained-memory or GC-time reduction.

## Reproduction

```sh
bun bench/ts/src/compare-costs.ts f51ad856e37d802b8865bb2870c3adebc293e7d1 .cache/cost-comparison
bun bench/ts/src/compare-costs.ts f51ad856e37d802b8865bb2870c3adebc293e7d1 .cache/host-repeat host/immediate
bun --cpu-prof --cpu-prof-name=before-transform.cpuprofile --cpu-prof-dir=.cache/cost-comparison .cache/cost-comparison/before.js profile macro/transform
bun --cpu-prof --cpu-prof-name=after-transform.cpuprofile --cpu-prof-dir=.cache/cost-comparison .cache/cost-comparison/after.js profile macro/transform
bun run bench --only zig,ts,applescript,gopher-lua --count 3
```

The comparison helper writes source hashes and every raw batch sample, then collects heap observations separately. Repeat the profile commands for `numbers/add` and `collections/list-append` for the other saved profiles. The optional third comparison argument selects an exact workload name. Source-map paths in raw profiles are Bun bundle-relative; the summary preserves the original source suffixes.
